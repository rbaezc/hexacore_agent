# Design Conventions

## From Requirement to Slices
1. List the use cases in the requirement ("place an order", "cancel an order", "issue an invoice").
2. Group use cases that share the same aggregate and invariants into one slice; split when they change for different reasons.
3. Name slices after the business capability (`orders`, `invoicing`), never after technical layers (`services`, `utils`).
4. A slice should be implementable and testable in isolation. If two candidate slices always change together, merge them.

## Contract-First APIs
- Define the HTTP contract of a slice (`define_contract`) before implementing presentation code.
- The contract lives in `contracts/<slice>.openapi.yaml` and is reviewed like code.
- Breaking changes to a published contract require a new version and an ADR.

## Architecture Decision Records (ADR)
Record a decision (`record_decision`) when:
- Choosing between alternatives that are expensive to reverse (database, messaging, sync vs. async boundaries).
- Accepting a rule exception (e.g. a justified cross-slice dependency warning).
- Introducing a new external dependency or framework.

An ADR states context, decision, alternatives considered and consequences. ADRs are immutable: supersede, don't edit.

## Persistence Design
- Start each slice with the in-memory adapter generated by HexaCore; replace it with a real adapter behind the same port.
- One aggregate per transaction; cross-aggregate consistency through domain events.
- See the database conventions for schema rules.

## Error Handling
- Domain/application errors are values or typed exceptions with a clear message; presentation maps them to protocol errors (HTTP 400/404/409).
- Never leak infrastructure exceptions (SQL, HTTP client) through the application layer.

## Session Discipline for Agents
- Start with `resume_session`; end with `record_handoff` (what was done, what's next, open questions).
- Preview generated code with `dryRun`; every HexaCore write is reversible via `rollback_changes`.

1. End-to-End Developer Workflow: How It Works

Do you need your target HexaGen project running before starting? No! HexaCore Agent acts as an autonomous local engine that interfaces with any project directory (existing or new). Here is the complete lifecycle:

Step 1 — One-Time Server Setup
Install & Build HexaCore Agent Engine

You build HexaCore Agent only once on your machine. This prepares the local Model Context Protocol (MCP) server executable.

Step 2 — IDE / AI Client Registration
Register MCP Config in Antigravity / Claude / Cursor

Configure your mcp.json pointing to HexaCore Agent. This connects the agent's "hands" directly to your AI chat interface.

Step 3 — Open Any HexaGen Project Workspace
Existing Project OR Greenfield (New) Project

Open your target project folder (e.g., my_rust_backend with Cargo.toml or my_elixir_app with mix.exs). HexaCore automatically senses the Project Detection File. If the directory is empty, HexaCore can scaffold the base project for you!

Step 4 — Autonomous Execution & QA Loop
Design, Build, Verify — with Every Write Reversible

Ask for a feature (e.g., "Create a payments slice"). Your AI client decomposes it into slices; HexaCore retrieves the applicable rules, generates slices adapted to your project (with tests), audits the architecture, and runs the stack's own compiler and test runner with structured results. When the client supports MCP sampling, failing tests are fixed through the client's model — never by editing tests — and any patch that makes things worse is rolled back.

3. System Overview & Core Architecture

HexaCore Agent operates locally on your machine via the Model Context Protocol (MCP). It enforces Vertical Slice Architecture (VSA) and strict architectural policies across your entire enterprise suite.

Vertical Slice Architecture

Features are organized into completely self-contained vertical slices. No monolithic horizontal layering or cross-slice coupling.

Embedded Local BM25 RAG

Calculates semantic term density over local technical documentation (/docs) using TF-IDF / BM25 without external API vector dependencies.

Circuit Breaker Resilience

Trips only on infrastructure failures (spawn errors, timeouts) — never on red tests — and kills hung process trees (dotnet test, mix test, vitest).

Security Sandbox Guard

Prevents path traversal attacks and blocks unsafe shell commands (rm -rf, format, chmod 777) before execution.

6. Exposed MCP Tool Catalog Reference

All tools are exposed natively to LLMs under the Model Context Protocol specification:

resume_session

Call first: briefing of unfinished plans, last QA results, decisions, last handoff and checkpoints, plus detected stacks.

search_knowledge_base

Bilingual BM25 search over bundled rules, project rules (.hexagen/rules) and ADRs (docs/adr).

execute_scaffolding

Generates a slice with tests and composition root, adapted to the host project. Never overwrites without overwrite:true; dryRun previews.

run_quality_assurance

test / typecheck / lint / build with the stack's own tools; structured failures with file and line; missing tools reported as skipped.

check_architecture

Audits cross-slice coupling, layer dependency direction and the 250-line limit across the workspace.

orchestrate_task

Runs a persisted plan: rules → scaffold each slice → architecture → QA (sampling-based auto-fix when available).

resume_plan

Continues a persisted plan from its first unfinished step.

list_checkpoints / rollback_changes

Every HexaCore write is checkpointed; rollback is all-or-nothing and refuses to clobber later edits unless forced.

record_decision

Writes an ADR to docs/adr/ and makes it retrievable in later sessions.

define_contract

Contract-first: writes contracts/<slice>.openapi.yaml (OpenAPI 3.1).

record_handoff

Leaves a summary, next steps and open questions for the next session.

8. Governance & Security Policies

  • Strict Line Count Limit (< 250 Lines): No generated or edited code file may exceed 250 lines of code. Enforced by automated Slice Policy Linter.
  • Mandatory Foreign Key Constraints: Relational database migrations must enforce strict FK constraints without exception.
  • Reversible Writes: Every file HexaCore writes is recorded in a checkpoint (.hexagen/checkpoints/) and can be rolled back exactly.
  • Tests Are the Specification: Automated fixes may never edit test files.
  • Atomic File Operations: All state modifications write to temporary files first before atomic kernel OS renames, preventing state corruption.
  • Circuit Breaker & Process Resilience: All sub-processes operate under automatic circuit breaker protection (CLOSED, OPEN, HALF_OPEN) with aggressive timeouts.

9. Troubleshooting & FAQ

What happens if a test fails during QA?

HexaCore returns structured failures (test, file, line, message). If your client supports MCP sampling, HexaCore asks your model for a search/replace fix to implementation code only, applies it through a checkpoint, re-tests, and rolls it back if things got worse. Otherwise the client model fixes the code and re-runs run_quality_assurance.

How does State Recovery work after a crash?

The AI client invokes resume_session on start. HexaCore reads .hexagen/state.json and returns a briefing: unfinished plans (continue with resume_plan), failing checks, recent ADRs and the last handoff note.

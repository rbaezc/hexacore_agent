Install

One line in the client you already use.

Node 20 or newer. HexaCore Agent reads the workspace from your client's MCP roots, so there is nothing else to configure.

Run in your terminal:

claude mcp add hexacore-agent -- npx -y hexacore-agent

Add to .cursor/mcp.json in your project (or ~/.cursor/mcp.json for every project):

{
  "mcpServers": {
    "hexacore-agent": {
      "command": "npx",
      "args": ["-y", "hexacore-agent"]
    }
  }
}

Add to .vscode/mcp.json in your project:

{
  "servers": {
    "hexacore-agent": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "hexacore-agent"]
    }
  }
}

Add to claude_desktop_config.json (Settings → Developer → Edit config):

{
  "mcpServers": {
    "hexacore-agent": {
      "command": "npx",
      "args": ["-y", "hexacore-agent"],
      "env": { "HEXACORE_WORKSPACE": "/path/to/your/project" }
    }
  }
}

Also listed in the MCP Registry as io.github.rbaezc/hexacore-agent. From source: clone the repo, npm install && npm run build, and point your client at node dist/cli/mcp_launcher.js.

Vertical slices

One feature, one folder, wired and tested.

HexaCore Agent scaffolds each feature as a vertical slice that follows your project's layout and naming. This is the Go slice from the session above, planned with dryRun before a single file is written.

$ hexacore scaffold go refunds --dryRun

internal/slices/refunds/
  domain.go        entities and rules
  service.go       use cases
  repository.go    port + adapter
  handler.go       HTTP entry point
  module.go        composition root
  service_test.go  tests first
domain

Depends on nothing outside the slice. The architecture audit fails if it imports an outer layer.

ports

Interfaces the slice needs, with adapters behind them, so tests swap real storage for fakes.

module

The only place where the slice is wired. Other slices use its public API, never its internals.

tests

Generated with the slice and run with your stack's own runner. They are the specification.

The loop

It learns from what your tests prove, not from what the model claims.

Every check that goes from red to green becomes evidence. A lesson earns credit only when the actual fix matches it.

  1. 1 red

    A check fails

    Your stack's own runner reports file, line and test. HexaCore Agent snapshots the project and offers lessons that match the failure.

  2. 2 fix

    The agent fixes it

    Every write goes through a checkpoint. A patch that makes things worse is rolled back, and tests are never edited.

  3. 3 green

    The diff is the evidence

    The green project is compared with the red snapshot. A lesson whose terms show up in the changed lines gets the credit.

  4. 4 lesson

    Proven lessons travel

    After 3 helps at 70% or better, a lesson becomes a Claude Code skill and joins your library in ~/.hexacore for your other projects.

↺ The next failure starts at step 1 with better lessons. Unused ones fade after 60 days, duplicates get merged.

UI prototypes

Design the screen first, and check it in a real browser.

Your agent writes the page; HexaCore Agent versions it, serves it on your machine, checks it at phone and desktop width in light and dark mode, and moves the approved version into your project.

  1. 1 v1, v2…

    Prototype

    create_prototype saves each version as a checkpoint and returns a preview on 127.0.0.1 that reloads by itself.

  2. 2 ui

    Check

    14 rules on the source, then Chromium at 390px and 1280px: overflow, contrast, clipped text, console errors, with screenshots the model can see.

  3. 3 green

    Learn

    A UI failure that turns green is an episode like a failing test. The next prototype gets the lesson before it repeats the mistake.

  4. 4 promote

    Ship it

    promote_prototype copies a page into place and checks it there, or hands a React or Flutter slice the tokens and markup to port.

/prototype_ui runs the whole flow. Browser checks need Playwright in the project: npm i -D playwright.

Writes you can undo

Every change goes through a checkpoint in .hexagen/checkpoints/, and rollback restores files exactly, or not at all.

Tests are the spec

Auto-fix patches implementation code only. A patch that leaves more failures than before is rolled back.

Small files

No generated or edited file may pass 250 lines. The slice linter and the architecture audit both enforce it.

Plain files you can commit

Plans, ADRs and QA history live in .hexagen/state.json. Lessons are markdown in .hexagen/skills/ you can review in a PR.

A profile you control

Preferences and observed habits stay in ~/.hexacore/profile.json. Text that looks like a credential is refused.

No corrupted state

State is written to a temporary file and renamed atomically. Toolchain processes run with timeouts behind a circuit breaker.

CLI

The same agent, from your terminal and CI.

Ships in the same package. JSON on stdout, and exit code 2 when checks are not green, so it drops into any pipeline.

# install once, or prefix each command with npx -p hexacore-agent
npm install -g hexacore-agent

# rule search, in English or Spanish
hexacore rag "reglas de capas en go"

# preview a slice, then write it
hexacore scaffold rust payments --dryRun --workspace ../shop
hexacore scaffold rust payments --workspace ../shop

# checks and the architecture audit (warnings fail with --strict)
hexacore qa rust --checks typecheck,test --workspace ../shop
hexacore arch --strict --workspace ../shop

# check a page, serve prototypes, promote one
hexacore ui landing --workspace ../shop
hexacore preview --open --workspace ../shop
hexacore promote landing docs/index.html --workspace ../shop

# what it has learned, and undo
hexacore lessons --workspace ../shop
hexacore rollback cp_7f3a --workspace ../shop
FAQ

Questions people ask first.

Does it need an API key or its own model?

No. HexaCore Agent runs on your machine as an MCP server and your client's model does the thinking. For auto-fix it asks that same model through MCP sampling, when the client supports it. Otherwise the client fixes the code and runs the checks again.

What happens when a test fails?

You get structured failures: test, file, line and message, plus any lessons that match. With sampling, HexaCore Agent requests a search-and-replace fix to implementation code, applies it through a checkpoint, re-runs the checks, and rolls it back if things got worse.

How do I continue tomorrow, or after a crash?

Your client calls resume_session at the start. It reads .hexagen/state.json and returns a briefing: unfinished plans (continue them with resume_plan), failing checks, recent ADRs, the last handoff note, your preferences and the most useful lessons.

Does it adapt to me?

Yes. When you state a lasting preference, the model saves it with remember_preference. HexaCore Agent also notices habits from how you use it: your stacks, the checks you run, whether you preview scaffolding, how often you roll back. Both open every briefing, and forget_preference removes them. HEXACORE_PROFILE=off turns the user profile off.

Can it design and check UI?

Yes. Your agent writes the page and HexaCore Agent keeps it honest: versions with rollback, a local preview, 14 static rules, and with Playwright installed, a real browser pass at phone and desktop width in light and dark mode. Approved pages are copied into place and checked again; for React, Flutter and other frameworks you get the design tokens and the steps to port it.

Can I use it in an existing project?

Yes. It detects the stack and the existing layout, and new slices follow your folders and naming. Add your own conventions as markdown in .hexagen/rules/ and your ADRs in docs/adr/; both are searched next to the bundled rules.
